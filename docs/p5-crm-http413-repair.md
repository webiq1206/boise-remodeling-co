# P5 CRM HTTP 413 repair

The CRM receiver source was read at commit `571c6f6d8009994325bf59bb322a74a65697eab5`. Its `server/index.ts` installs `express.json()` without a custom limit, so the effective JSON body limit is the Express/body-parser default of 100 KiB. The `/api/external/leads` handler in `server/routes.ts` accepts `fullName` and `email`, maps the intake fields to a lead, and stores `estimate`, `estimateSummary`, range, and property as serialized `sourcePayload`. The imported `externalLeadSchema` and `validateRequest` were subsequently obtained from the authenticated `server/validation.ts` snapshot at that same commit; the exact relevant definitions are imported by the offline contract test.

The sender now targets 90,000 UTF-8 bytes. When it fits, it keeps the complete scope, customer estimate, internal priced lines, and distinct internal assumptions, exclusions, and allowances. It omits only a byte-identical internal scope copy, policy/cost-book snapshots, and long line-level source narratives repeated in those pricing sources. That copy contains an explicit path, count, and reason manifest plus an authenticated estimator-admin reference to the unchanged durable draft/outbox payload.

If that legitimate compact estimate still exceeds the sender bound, the request changes to an explicitly labelled `authenticated-reference` envelope rather than making an all-scope copy or silently dropping fields. The bounded envelope contains the exact lead identity, nested sender/source identity, estimate ID and revision, service, an explicitly measured summary excerpt, selling range, and a manifest naming the complete scope, internal pricing/evidence, and customer presentation that remain in the unchanged saved draft and outbox record. It does not hide another scope or body in a summary field. Its deep link is `/admin/p5-estimators?id=<draft UUID>&revision=<revision>`; the page validates the UUID and revision before issuing an encoded request. The existing authenticated GET handler resolves that exact current or immutable historical revision and marks historical responses read-only. Normal estimator-admin authentication remains required. The URL does not grant public access or bypass authentication. If even the minimal reference envelope cannot fit, construction fails explicitly. The configured sender domain is hostname-validated before it is used in source metadata or the admin URL.

The two locally saved failed records were exercised offline. The exact original sender construction produced request bodies of 134,278 and 147,927 UTF-8 bytes. The repaired request bodies are 73,571 and 81,327 bytes, respectively. (The unchanged durable outbox JSON records themselves are 112,889 and 126,666 bytes and are not the HTTP request-size measurement.) Both repaired requests passed the reproduced 102,400-byte parser gate, the pinned actual Zod schema, and the extracted handler auth/validation/persistence path with mocked auth and storage. No request, provider operation, database write, retry, or delivery-status change was performed. Tests use a redacted, structurally equivalent, meaningfully oversized synthetic fixture; production customer payloads are not committed.

Receiver evidence covers the authenticated pinned `server/index.ts`, `server/routes.ts`, `shared/schema.ts`, and subsequently fetched `server/validation.ts`. The offline test reproduces the parser byte gate, imports the actual `externalLeadSchema`/`validateRequest` excerpt, and executes the extracted handler's Bearer authentication, validation, unknown-key stripping, and `sourcePayload` persistence transformation against mocks. It establishes source-compatible offline acceptance, not live deployment, proxy, notification side-effect, or real-database acceptance.

The oversized-reference regression uses a realistic synthetic estimate above 90 KB, verifies the envelope against that same offline legacy receiver schema and extracted handler, and validates that the reference targets the authenticated admin page's supported draft-ID and revision GET contract. This old schema coverage is not coverage of the pending keyed authenticated QA receiver contract. The test performs no live CRM call, provider operation, database write, retry, or delivery-ledger modification. The pinned receiver strips top-level `externalLeadId`; the envelope therefore also retains source and estimate identity inside its accepted `estimate` object. Its observed duplicate behavior is email-based HTTP 409, so neither that field nor the test is treated as proof of receipt or idempotency.

Only `CRM returned HTTP 413` was retained for the historical failures, so the exact original response body is unavailable. CRM responses are now read to a maximum of 64 KiB. An oversized response is never partially parsed as an acknowledgement and instead enters the existing CRM reconciliation path. Future failures report bounded, non-PII diagnostics: HTTP status, request/response byte counts, a fixed content class (`json`, `text`, `other`, or `missing`), and presence of fixed allowlisted acknowledgement/error keys. Raw content types, arbitrary object keys, response values, credentials, contact data, and payload content are not included. A successful response still requires a non-false acknowledgement and a CRM record identifier.
